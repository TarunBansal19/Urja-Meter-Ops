1.​ Source code for your API service.
2.​ README — the front door to your submission. We should be able to understand, run, and evaluate
everything from here. It must contain (or clearly link to) all of: what you built and how it's structured,
how to install/configure/run it, a sample request, your assumptions, design decisions & trade-offs,
what you intentionally skipped, what you'd improve with more time, and where to find PROTOCOL.md
and openapi.json. Assume the reader has zero prior context.
3.​ PROTOCOL.md — a short write-up of how the portal actually works, as you discovered it: what data
is available, how you get to it, how access/auth works, and any quirks or surprises you found. This
is one of the most valuable things you'll submit.
4.​ openapi.json — an OpenAPI (3.x) description of your API — the clean one you're building, not
the portal's. How you produce it is up to you (by hand, from code annotations, or a generator).
Optionally, serve a rendered view of it (e.g. Scalar, Swagger UI, or Redoc) so it can be explored in a
browser.
5.​ Notes (can live in the README) covering:
-​ Assumptions you made.
-​ Design decisions and trade-offs.
-​ What you intentionally left out, and why.
-​ What you'd improve or do differently with more time.
6.​ Reflection — the questions below, answered in your README or a linked REFLECTION.md.

Put your answers in your README (a ## Reflection section) or in a REFLECTION.md linked from the
README. A paragraph each is plenty:

What assumptions did you make?
Which part was the most difficult, and how did you get unstuck?
If you had another day, what would you improve?
What mistake did you make while solving this (there's always one)?
If you were reviewing your own submission, what would you criticise?
